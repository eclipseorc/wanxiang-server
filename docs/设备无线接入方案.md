# 设备无线接入方案（scrcpy 远程控制的 ADB 连接策略）

本文档回答一个核心问题：**共享测试设备在「需移动、未 root、内网互通、IP 可能变化」的前提下，如何让 scrcpy 远程控制的 ADB 连接尽量少依赖数据线、少人工操作。**

本文是方案设计文档，用于团队评审后决定是否落地实现。落地时需按 `AGENTS.md` 的维护约定同步更新 README 与相关接口文档。

---

## 1. 背景与问题

### 1.1 现状

远程屏幕控制走 scrcpy，依赖 ADB 无线连接。设备接入分两种模式：

- **无线调试模式**（Android 11+，多数设备）：配对（`adb pair`，6 位配对码）→ 连接（`adb connect`，动态端口）。
- **传统模式**（`adb tcpip`，Android 11 及更早 / 部分厂商 ROM）：USB 连一次切 `adb tcpip 5555` → 拔线走 `IP:5555`。

### 1.2 观察到的痛点

1. 设备长时间运行后，浏览器静止断连或手机端进程被杀，导致 ADB 连接断开。
2. 手机端 App 的**业务 WebSocket 心跳**能自动重连（所以管理后台显示设备「在线」），但 **ADB 无线连接不会自动恢复**（`adb devices` 为空）。
3. 前端曾出现「假完成」：`adb devices` 为空时，配对/连接两步仍被标记为「已完成」，点「开始控制」才报「会话已结束」。该 bug 已修复（见 §5）。
4. 用户核心诉求：**尽量零数据线、零人工操作**。

### 1.3 关键前提（已与用户确认）

| 约束 | 结论 |
| --- | --- |
| 设备是否固定 | 需移动，不能 USB 常连 |
| 是否 root | 未 root，App 无法自行切换 adbd 状态 |
| 网络 | 内网互通；IP 大部分固定，但路由器重启可能重新分配 |
| 「无线调试」普及 | 部分设备有，部分无（Android 11 及更早 / 厂商 ROM） |

---

## 2. 技术结论（为什么「彻底零数据线」不可行）

### 2.1 系统安全边界

Android 的 `adbd` 要接受**网络连接**，必须建立一次「可信初始化」，两条路径二选一：

1. **USB 授权**：插一次数据线，在手机上点「允许 USB 调试」。
2. **无线调试配对**（Android 11+）：用配对码 / 扫码建立 TLS 加密信任。

两者本质都是「建立这台电脑可信」的凭证。**未 root 时，没有任何 App 能替用户完成这一步**——否则恶意 App 就能把手机变成可远程控制的肉鸡，这是系统绝对禁止的。

### 2.2 因此，两种设备的上限如下

| 设备类型 | 首次接入 | 日常控制 | 设备重启后 |
| --- | --- | --- | --- |
| 有「无线调试」 | 纯无线配对（30 秒） | 纯无线 | 需在手机上重新打开「无线调试」开关（3 秒，端口会变） |
| 无「无线调试」 | **需插一次数据线**切 tcpip | 纯无线 | **需再插一次数据线**切 tcpip |

> 唯一的、无法消除的人工动作：
> - 有「无线调试」的设备 → 重启后在手机上重开「无线调试」开关。
> - 无「无线调试」的设备 → 首次 + 每次重启各插一次数据线。
>
> 只有 Android 17 的 ADB Wi-Fi 2.0（配 adb 37.0.0+）能做到「可信网络下自动重连」，暂不适用于现有设备。

## 3. 关键技术发现（据 ADB 官方文档与社区实践核实）

1. **配对信任是持久的**：`adb pair` 产生的信任（服务器 `~/.android/adbkey`）长期有效，**配对只需一次**，变化的只是连接端口。
2. **`adb tcpip 5555` 可通过无线通道执行**：不需要 USB 线。只要存在一条已建立的 ADB 连接（无论 USB 还是无线调试），就能把 adbd 切到 5555 固定端口监听，**直到设备重启**。
3. **mDNS 自动发现**：ADB 31.0.2+ 支持 `adb mdns services` / `ADB_MDNS_AUTO_CONNECT`，设备在局域网广播 `_adb-tls-connect._tcp`，服务器可自动发现并自动连接**已配对**的设备，从而规避「IP 变化 + 端口变化」两个痛点。
4. **端口变化规律**：Android 11–16 的「无线调试」在重启 / 切换网络后会关闭，重开后连接端口随机变化；配对端口与连接端口都动态。

### 3.1 由此推导出的最优路径（有「无线调试」的设备）

```
首次（纯无线，约 30 秒，零数据线）：
  1. 手机打开「无线调试」
  2. adb pair IP:配对端口 配对码        # 建立持久信任
  3. adb connect IP:临时连接端口        # 连接
  4. adb -s IP:临时端口 tcpip 5555     # 通过无线通道切固定端口（关键！）

之后每次设备重启（零数据线，唯一人工动作 = 重开「无线调试」开关）：
  1. 手机重新打开「无线调试」开关（3 秒）
  2. 后端通过 mDNS 自动发现设备 → 自动 connect → 自动切 5555
  （若不做 mDNS，则后端用固定 IP + 5555 重连）
```

## 4. 建议的分阶段实施方案

### 阶段 1（核心，收益直接）：配对后自动切固定端口 5555

**目标**：让「配对的临时端口」不再成为后续重连的负担。

**改动**：
- 后端新增「一键接入」流程：`pair` → `connect` → `tcpip 5555`，或在前端「配对成功」后自动触发 `tcpip`。
- 前端配对/连接成功后提示「已切换为固定端口 5555，之后可直接用 IP:5555 重连」。
- 将设备的固定端口（5555）与 IP 一起持久化，重连时优先用固定端口。

**收益**：配对后设备监听固定 5555，掉线重连不再依赖临时端口。

### 阶段 2（自动化）：mDNS 自动发现 + 自动重连

**目标**：设备重启后，用户只需在手机上重开「无线调试」开关，后端自动发现并连上，且自动切 5555。

**改动**：
- 后端周期扫描 `adb mdns services`（或启用 `ADB_MDNS_AUTO_CONNECT` 只自动连接已配对设备）。
- 对发现的已配对设备自动 `connect` + `tcpip 5555`。
- 兜底：设备 IP 变化时，mDNS 能提供最新地址，避免依赖固定 IP。

**收益**：把「重启后重连」的人工操作降到只剩「手机上重开开关」。

**依赖**：
- adb 版本 ≥ 31.0.2，且开启 mDNS（`ADB_MDNS_OPENSCREEN=1`）。
- 内网无 mDNS 广播抑制（企业 Wi-Fi 可能禁用组播，需实测）。

### 阶段 3（兜底）：无「无线调试」设备的现状保持

**目标**：对无「无线调试」的少数设备，接受「首次 + 每次重启插一次线」的现实，配合前端如实提示，不做过度工程。

**改动**：
- 前端如实标注「ADB 未连接」状态，不再「假完成」（已实现，见 §5）。
- 提供清晰的接线 / 切 tcpip 操作 SOP（见 §7）。

## 5. 已完成的修复（本轮）

### 5.1 前端「假完成」状态修复

**问题**：`restoreFromBackend()` 在 `adb devices` 为空（设备未连接）时，无条件把「配对」「连接」两步标记为「已完成」，点「开始控制」才失败。

**修复**：
- 后端 `adb.Connect` 增加真实校验：`adb connect` 后轮询等待设备进入 `device` 状态（8 秒超时），失败返回明确错误（区分 unauthorized / not online）。
- 前端 `restoreFromBackend` 严格以 `/api/admin/scrcpy/status` 的真实 `device` 状态为准，重连失败时如实显示「设备未连接」，不伪造成功。

### 5.2 僵尸 scrcpy-server 进程清理

**问题**：设备掉线重连后，设备上残留的旧 scrcpy-server 进程占着 `localabstract:scrcpy` socket，导致新会话连到僵尸 socket 失败。

**修复**：`start()` 启动新 scrcpy-server 前先 `pkill -f genymobile.scrcpy.Server` 杀旧进程并等 socket 释放。

### 5.3 错误原因可诊断

**问题**：`prepare` 失败时前端只看到笼统的「会话已结束」。

**修复**：把 `prepare`/`tryAcquire` 移到 WS 升级之后，失败通过 WS `error` 消息下发；前端 `lastError` 机制展示真实原因。

## 6. 待评审的开放问题

1. **是否引入 mDNS**：mDNS 自动发现需要内网支持组播，且要处理「发现到未配对设备」的过滤（只连已配对设备）。建议先做阶段 1，实测 mDNS 可用性后再做阶段 2。
2. **固定端口的取舍**：`tcpip 5555` 是明文 TCP（无 TLS 加密），相比「无线调试」的 TLS 配对安全性弱。内网共享测试设备场景可接受，但需团队确认安全边界。
3. **设备 IP 管理**：是否引入 DHCP 静态租约 / 设备 IP 登记表，减少 IP 变化的兜底成本（mDNS 可缓解，但静态租约更稳）。

## 7. 操作 SOP（运维参考）

### 7.1 有「无线调试」的设备

| 步骤 | 操作 | 频率 |
| --- | --- | --- |
| 1 | 手机打开「无线调试」，后台录入 IP + 配对端口 + 配对码 | 首次一次 |
| 2 | 后台自动 connect + tcpip 5555 | 自动 |
| 3 | 日常控制 | 无线，固定 5555 |
| 4 | 设备重启后：手机重开「无线调试」开关 | 每次重启，3 秒 |

### 7.2 无「无线调试」的设备

| 步骤 | 操作 | 频率 |
| --- | --- | --- |
| 1 | USB 连电脑，开「USB 调试」，后台切 tcpip 5555 | 首次 + 每次重启 |
| 2 | 拔线，走 IP:5555 | 日常无线 |

---

## 8. 结论

在「需移动 + 未 root」的硬约束下，「彻底零数据线」不可行。但通过「配对后切固定端口 5555 + mDNS 自动发现」，可以把有「无线调试」设备的日常接入体验做到接近零人工（唯一动作是重启后重开开关）。无「无线调试」的少数设备则接受「偶尔插线」的现实。

建议先落地**阶段 1**（收益直接、改动可控），实测后评估**阶段 2**（mDNS 自动化）。
